# تصميم بقاء محتوى الصفحة الرئيسية دون إنترنت

التاريخ: 2026-08-13

## المشكلة

تعرض الصفحة الرئيسية معاينات حية من Supabase لقسمي «وصفات رائجة» و«تعرّف على الجلوتين». دوال المعاينات تقرأ من كاش الوصفات والمقالات عند فشل الشبكة، لكنها لا تحفظ نتائج المعاينات الناجحة فيه. لذلك يبقى الكاش فارغًا إذا اكتفى المستخدم بزيارة الصفحة الرئيسية، ويختفي المحتوى بعد انقطاع الإنترنت.

كاش الـPWA الحالي يحفظ ملفات التطبيق والخطوط، لكنه لا يحفظ صور Supabase الخاصة بالوصفات والمقالات.

## معيار النجاح

بعد أول تحميل ناجح لكل قسم:

- تظهر آخر معاينات محفوظة فورًا عند فتح الصفحة.
- يحاول التطبيق جلب النسخة الأحدث من Supabase في الخلفية عند توفر الشبكة.
- يستبدل المحتوى الظاهر بالنسخة الأحدث بعد نجاح الطلب.
- يبقى آخر كاش صالح عند فشل الطلب أو انقطاع الإنترنت.
- تبقى صور المحتوى التي سبق تحميلها متاحة في نسخة الويب المثبتة ضمن حدود التخزين المحددة.

لا يشمل هذا التصميم تشغيل القسمين عند أول فتح للتطبيق قبل حدوث أي تحميل ناجح للمحتوى.

## التصميم المعتمد

### 1. كاش معاينات مستقل

تُحفظ معاينات الصفحة الرئيسية في مخزن `meta` الموجود داخل IndexedDB بمفتاحين مستقلين:

- `recipePreviews`
- `articlePreviews`

هذا يمنع المعاينات المختصرة من استبدال سجلات الوصفات والمقالات الكاملة أو حذف تفاصيل مثل المقادير والخطوات ومحتوى المقالة. لا يحتاج الحل إلى رفع إصدار قاعدة IndexedDB أو إنشاء object stores جديدة.

تضاف دوال صغيرة ومحددة الغرض في `services/db.ts` لقراءة وكتابة كل قائمة، مع الاحتفاظ بحد أقصى 7 وصفات و5 مقالات.

### 2. تدفق Stale-While-Revalidate داخل الواجهة

عند تركيب `TrendingRecipes` أو `KnowledgeHub`:

1. يبدأ طلب الكاش وطلب Supabase دون انتظار أحدهما لبدء الآخر.
2. إذا وصل الكاش أولًا وكان غير فارغ، يعرض فورًا وينتهي وضع التحميل.
3. إذا نجح طلب Supabase، تُعرض البيانات الأحدث وتُحفظ في كاش المعاينات.
4. إذا فشل Supabase، يبقى المحتوى المحفوظ ظاهرًا.
5. إذا لم يوجد كاش وفشل الطلب، يستخدم كل قسم حالة الفراغ الحالية دون تعطيل بقية الصفحة.
6. تتجاهل الطلبات نتائجها بعد إزالة المكوّن لتجنب تحديث state بعد unmount.

دوال Supabase تبقى مسؤولة عن جلب البيانات وتحويلها وحفظ نتيجة الشبكة الناجحة. المكونات مسؤولة فقط عن عرض الكاش سريعًا ثم قبول التحديث الحي.

الاستجابة الناجحة الفارغة تمثل حذف المحتوى من الإدارة، ولذلك يجوز لها تحديث الكاش إلى قائمة فارغة. فشل الشبكة أو الاستثناء لا يمسح آخر كاش صالح.

### 3. كاش صور المحتوى

يضاف Runtime Cache محدود في `vite.config.ts` لطلبات القراءة العامة من Supabase Storage باستخدام `CacheFirst`:

- اسم مستقل للكاش.
- حد أقصى 80 صورة.
- عمر أقصى 30 يومًا.
- قبول الاستجابات الناجحة وopaque فقط.

لا تُخزن طلبات Supabase REST أو الطلبات الإدارية في Workbox، لتجنب خلط استجابات تعتمد على صلاحيات أو رؤوس توثيق مختلفة. داخل Android تبقى بيانات النص مضمونة عبر IndexedDB، بينما صور الشبكة تخضع أيضًا لكاش WebView المتاح على الجهاز.

## الملفات المتأثرة

- `services/db.ts`: دوال كاش المعاينات.
- `services/supabaseService.ts`: حفظ نتائج المعاينات الناجحة والرجوع إلى كاش المعاينات المخصص.
- `components/blog/TrendingRecipes.tsx`: عرض الكاش أولًا ثم تحديثه حيًا.
- `pages/KnowledgeHub.tsx`: عرض الكاش أولًا ثم تحديثه حيًا.
- `vite.config.ts`: كاش صور Supabase Storage.
- `tests/`: اختبارات انحدار لسلوك البيانات وإعداد Workbox.
- `AGENTS.md` و`context/status.md` و`context/domains/frontend-admin.md`: توثيق السلوك بعد اكتمال التنفيذ.

## الاختبارات والتحقق

يبدأ التنفيذ باختبارات فاشلة تثبت أن:

- دوال المعاينات تحفظ نتيجة الشبكة الناجحة في الكاش المخصص.
- فشل الشبكة يعيد كاش المعاينات بدل مصفوفة فارغة.
- المكونات تقرأ الكاش قبل اكتمال التحديث الحي ولا تخفي المحتوى عند فشل التحديث.
- Workbox يطابق صور Supabase Storage فقط ضمن الحدود المعتمدة.

بعد نجاح الاختبارات:

- تشغيل مجموعة الاختبارات كاملة.
- تشغيل build إنتاجي.
- تشغيل مزامنة Capacitor مع Android.
- اختبار متصفح إنتاجي بالتسلسل: تحميل أونلاين، التحقق من امتلاء الكاش، قطع الشبكة، التنقل بعيدًا والعودة، ثم التأكد من ظهور القسمين والمحتوى المحفوظ.

## خارج النطاق

- تضمين محتوى افتراضي ثابت لأول تشغيل دون إنترنت.
- تخزين فيديوهات YouTube أو تشغيلها دون إنترنت.
- تخزين جميع صور المنتجات أو كل استجابات Supabase في Workbox.
- تغيير تصميم البطاقات أو نصوص حالات الفراغ.
